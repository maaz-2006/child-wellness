## 1. Summary

Kito is a web platform that helps a single school notice and respond to changes
in a child's emotional wellbeing, academic progress, social development and
healthy habits. The submitted artefact was designed, built and evaluated without
recruiting children, parents, teachers or any other human participant. All
wellbeing records in the demonstration database are generated by
`manage.py seed_demo` from a fixed random seed. The evaluation uses automated
tests, a replay of the alert rules against the generator's labels, an offline
machine-learning benchmark, and authenticated checks against the deployed site
using demonstration accounts.

The project therefore has **no human-subjects risk from participation**. It does
have a design ethics: the artefact handles data that, in a real school, would be
special-category health data about children. A substantial part of the design and
evaluation is about refusing capabilities that would make such a system harmful
if it were deployed.

|---|---|---|
| Child names, dates of birth, year group | generated by `seed_demo` | no — synthetic |
| Guardianships and mentorships | generated by `seed_demo` | no — synthetic |

| Messages | generated template text | no — synthetic |
| Audit log | writes performed during seeding and testing | no — synthetic actors |
| Model report | aggregate metrics and coefficients only | no — no child identifier |

The generator is deterministic for a given seed: the same command produces the
same cohort and the same trajectories. The names are drawn from a fixed list and
are not those of real pupils known to the author. The demo password is published
in `README.md`; the database contains nothing that would matter if it were read.

No free-text field in the submitted database contains a real person's writing.
No uploads are accepted by the platform. No analytics, advertising, tracking
pixel, third-party script or external API receives data from the application.

## 3. Ethical issues in the design

The project treats the following as ethical requirements, not features.

### 3.1 The child is not given a risk label

A child account has `SCORE: NONE` and `ALERT: NONE`. The child cannot open their
own trend page, see a tier, or read a case note, even about themselves. This is a
deliberate limit on the child's access to their own record: a system that tells a
child "you are in the urgent category" can cause harm, and the child is not in a
position to contest the label. The child can still see their own check-ins and
habits, and can ask an adult.

### 3.2 The administrator is powerful but not omniscient

The administrator can manage accounts, consent and configuration, and can see
cohort aggregates. They cannot read emotional check-ins, observations, case notes
or messages. This is a direct response to the common failure in commercial
wellbeing products where a tenant administrator can read everything. The head or
business manager does not need a child's diary to run the school.

### 3.3 Consent is a gate, not a checkbox

A guardian relationship grants access only while a consent record is current and
unrevoked. Revocation takes effect on the next request and does not delete
history. A child without consent cannot submit a check-in. This models consent as
an ongoing condition rather than a signature collected once.

### 3.4 A disclosure is not copied into a less-protected table

The safeguarding screen raises an urgent alert containing the matched category,
the date and an entry reference. It never stores the note text on the alert. The
sentence stays in the domain table under that domain's access rule. A
safeguarding queue must not become a second, less-protected copy of a child's
diary.

### 3.5 Every automated finding ends with a named person

Alerts are assigned to a named member of staff, preferably the designated
safeguarding lead for urgent findings. Nothing auto-resolves. A person decides
that a case is closed. The timeline is append-only, so a decision cannot be
quietly rewritten.

### 3.6 The model is not in the care path

The logistic regression is an offline benchmark. Its stored output is aggregate
metrics and coefficients, with no child identifier and no per-child prediction.
The report page says, in the interface, that it is not a decision system. This
prevents a research artefact from becoming a de facto risk score for a child.

## 4. Risk assessment for the submitted project

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| A synthetic record is mistaken for a real child's data | low | medium | every child carries a `ScenarioLabel`; `seed_demo` only touches labelled demo rows; documentation states the data are synthetic |
| The published demo password is reused by a real deployment | low | high | demo password is documented as demo-only; a real deployment must create new accounts and a new secret key; `DEPLOY.md` says so |
| The public URL exposes data during marking | low | medium | only synthetic data; admin account has its own password; no real personal data is present |
| A reviewer assumes ethics approval was granted | medium | medium | this statement states plainly that no participants were involved and that the ethics reference is a placeholder |
| The design is mistaken for a validated clinical tool | medium | high | report, README and model page all state that thresholds are not clinically validated and the model is offline |
| A future maintainer connects the model to alerts | low | high | model module has no production caller; report page is admin-only and audited; the design rationale is documented |
| Synthetic data encode a stereotype or a biased archetype | medium | medium | archetypes are behavioural, not demographic; the limitation is stated; a real pilot must audit subgroup performance |
| A real deployment inherits SQLite and loses data under load | low | medium | limitation stated; PostgreSQL is the documented migration path |

No risk in the submitted project involves a real person, so no risk requires
participant support, debriefing or withdrawal. The residual risks are about
misinterpretation and future reuse, and are addressed by documentation and by
keeping the model out of the decision path.

## 5. Ethics protocol for a future pilot

The following would be required **before** any real child, parent or staff member
uses the system. None of it was carried out in this project.

### 5.1 Approvals

1. University research ethics committee approval, with the protocol, information
   sheets, consent forms, assent script and DPIA attached.
2. School approval from the head and the designated safeguarding lead, with a
   named school contact.
3. A data processing agreement between the university and the school defining
   controller and processor roles.
4. A DPIA signed off before the first real record is created.
5. A safeguarding protocol covering what to do if a child discloses harm during
   the pilot, including out-of-hours contact and escalation.

### 5.2 Participants and recruitment

- **Children:** recruited through the school, with guardian consent and the
  child's own assent. Participation is voluntary and can stop at any time without
  explanation and without affecting schooling.
- **Parents/guardians:** recruited by the school, not by the researcher, to avoid
  pressure. Consent covers their own pulse responses and permits the child's
  participation.
- **Staff:** mentors and the safeguarding lead, recruited voluntarily; their line
  manager is not told who declined.
- **Exclusion:** any child subject to an active safeguarding investigation, or
  whose guardian lacks capacity to consent, would be excluded on the school's
  advice.

### 5.3 Consent model

Consent would be:

- **informed** — the information sheet states what is collected, why, who can see
  it, how long it is kept and how to withdraw;
- **specific** — separate consent for the child's check-ins, the guardian's pulse,
  and the use of anonymised aggregates in the write-up;
- **current** — recorded with a version and a timestamp, and revocable at any time
  through the school or the platform;
- **granular** — a guardian can withdraw the pulse without withdrawing the child's
  check-ins, and vice versa;
- **not a condition of schooling** — no child is disadvantaged by declining.

Withdrawal stops future processing immediately. It does not delete records that
have already contributed to an aggregate, but the record is excluded from any
future analysis. The information sheet says this in plain language.

### 5.4 Data protection

| Question | Answer for the pilot |
|---|---|
| Controller | the school, with the university as a joint controller for research analysis or a processor under a written agreement |
| Lawful basis (UK GDPR Art. 6) | public task for the school's pastoral function; consent for the research analysis |
| Special-category condition (Art. 9) | explicit consent for research; substantial public interest (safeguarding) for the operational record, with the school's policy cited |
| Data minimisation | only the four domains, no free-text case notes in the research extract, no uploads |
| Purpose limitation | operational support and the named research questions only; no marketing, no profiling, no sale |
| Storage limitation | raw records kept for the pilot plus `[RETENTION PERIOD]`; aggregates kept for the write-up; then deleted or anonymised |
| Security | role-aware access, TLS, hashed passwords, append-only audit, encrypted backups, no public export |
| International transfer | none; hosting in the UK/EU, or a documented safeguard if not |
| Rights | access, rectification, erasure where compatible with safeguarding, restriction, objection, and complaint to the ICO |
| Children's rights | ICO Age Appropriate Design Code standards applied; best interests, high privacy by default, transparency at the child's reading level |
| Breach | school and university notified within 24 hours; ICO within 72 hours if the threshold is met; affected families informed |

### 5.5 DPIA summary

A pilot DPIA would need to cover:

1. **Necessity and proportionality** — why four domains, why daily, why not
   less.
2. **Nature of the data** — special-category health data about children,
   including inferred mental-health signals.
3. **Risks to children** — stigma, labelling, bullying if data leak, effect on
   the child–teacher relationship, false positives leading to unnecessary
   intervention.
4. **Risks to parents** — exclusion, pressure to disclose, misreading a score.
5. **Risks to staff** — workload, liability, pressure to act beyond competence.
6. **Mitigations** — the design controls in Section 3, plus training, a named
   lead, a complaints route, and a kill switch to suspend the pilot.
7. **Consultation** — children, parents and staff on the information sheet and
   the family page, before launch.
8. **Sign-off** — head, DPO, ethics committee, with a review date.

Deletion would be tested, not assumed: a scheduled job plus a manual check, with
a log entry recording that it ran.

### 5.7 Benefits, harms and dissemination

The potential benefit is earlier, better-coordinated support for children whose
difficulties are currently invisible across separate systems. The potential harms
are stigma, surveillance, false accusation, reduced trust and workload. The pilot
would be designed so that participation is not required for support, and so that
a child or family can leave without losing access to help.

Results would be reported in aggregate. No child would be named or made
identifiable. The school would see its own operational data; the university would
see a pseudonymised extract. Any quotation from a free-text field would require
separate, specific consent and would be checked for indirect identifiers.

## 6. Research integrity

- The report distinguishes what was measured from what was assumed.
- The ML metrics are labelled as an offline benchmark on synthetic labels, not as
  a clinical prediction.
- The alert backtest is labelled as a test against a generator, not against real
  outcomes.
- No result is reported that cannot be regenerated from the repository.
- The report drafts are the student's responsibility; they must be rewritten in
  the student's own voice and checked against the module's academic-integrity
  policy.
