# 7. Discussion

## 7.1 What the evaluation actually shows

The results support a narrower claim than "the platform works". They support four
specific claims:

1. **The access model is real.** The matrix is the only authority, it fails
   closed, and 128 tests plus a live four-role check confirm that parents,
   mentors, children and the administrator receive different views of the same
   data. The strongest evidence is not that permitted pages render but that
   adjacent roles are refused, denied loudly, and audited.
2. **The scoring method is reproducible and honest about absence.** A window with
   no data produces no row, an overall score requires two domains, and recompute
   is idempotent. The gap behaviour is tested at the scoring layer and at the
   chart layer, which are the two places where absence can be silently converted
   into a zero.
3. **The alert rules detect the simulated declines and are operationally
   conservative.** Seven of seven positives were detected, three of fifteen
   negative children triggered at least once, and the median onset-to-alert
   interval was ten days. The engine keeps one rolling alert per rule, never
   downgrades, never auto-resolves and always names an owner.
4. **The structured features carry signal.** The leave-one-child-out classifier
   reached AUC 0.949 and accuracy 0.949 on held-out children. That is evidence
   about the features and the generator, not about clinical prediction, and the
   design deliberately keeps it out of the care path.

What the evaluation does **not** show is equally important. It does not show that
the thresholds are clinically appropriate, that children will use the check-in,
that mentors will trust the queue, or that the system improves any outcome. Those
are empirical questions for a pilot, and no pilot was possible within the
project's ethics and time constraints.

## 7.2 The central trade-off: governance before features

The design decision that shaped everything else was to build the permission model
before the features that depend on it. That ordering cost time early: the first
working page was a login and a matrix, not a dashboard. It paid back in three
ways.

First, every later view inherited a gate rather than reimplementing one. The
number of places where a permission bug could hide stayed small. Second, the
matrix became a design tool: writing the grants forced explicit answers to
questions such as "may a mentor read a child's private note?" and "may the
administrator see a case note?". Those questions are easy to leave ambiguous in a
requirements document and impossible to leave ambiguous in a dictionary that the
tests execute. Third, the matrix can be rendered into the interface from the code
that enforces it, so the documentation shown to staff cannot drift from behaviour.

The cost is that the project owns its authorisation code instead of delegating it
to Django's model permissions. That is a real maintenance burden, and it is why
the permission suite is the largest single block of tests. For a production
system with many resources, a mature object-level permission library might be the
better choice. For a project whose contribution *is* the access model, owning it
is the point.

## 7.3 Deterministic rules versus machine learning

The project kept both, in different roles. The rules decide; the model measures.
That separation is the most defensible thing in the design, and it was not the
original plan. The tempting version of this project deploys the classifier and
presents its probability as a risk score. The evaluation shows why that would be
a mistake: the model is trained on labels generated by the same synthetic
trajectories that the features summarise, so its high AUC partly measures
circularity. On real data, with real outcomes and a base rate near 0.24, the same
model would need calibration, drift monitoring and a prospective evaluation
before anyone should act on it.

The rules have the opposite property. They are less accurate in a statistical
sense, but a mentor can read one and answer "why did this fire?" without a data
scientist. In a safeguarding context, explainability is not a nice-to-have; it is
the condition under which a professional can exercise judgement. Rudin's (2019)
argument for inherently interpretable models in high-stakes decisions applies
with force here, and the project's response is to keep the decision layer simple
enough to audit.

There is a third option the project did not take: use the model only to rank the
queue, with the rules still deciding whether an alert exists. That would be a
reasonable future experiment, but it would require a prospective study to show
that ranking improves outcomes without amplifying bias. It is future work, not a
feature to smuggle into a submission.

## 7.4 Privacy as an architectural property

The privacy claims in this project are not policy statements; they are structural.

- A child cannot see their own score because the resource grant is `NONE`, not
  because the template hides it.
- An administrator cannot read a note because the institution grants exclude the
  content resources, not because the admin page omits a column.
- Consent removal takes effect on the next request because the relationship
  resolver requires a current, unrevoked row.
- A safeguarding alert cannot leak the disclosure because the alert stores a
  category and an entry reference, and the text never enters the alert table.
- A message cannot be edited because the model refuses `save()` on an existing
  row.

Each of these could have been implemented as a UI convention. The difference
matters when someone opens the database, writes a script, or adds a new view six
months later. Nissenbaum's (2009) contextual integrity is the right frame: the
question is not "is this data secret?" but "does this flow match the norms under
which the data was shared?". A role check cannot answer that; a relationship-aware
grant can.

The honest limitation is that the project cannot prove the absence of a leak. It
can show that the tested paths behave, that denials are audited, and that the
sensitive content is not copied into lower-protected tables. A penetration test
and a code review by someone outside the project would be the next step.

## 7.5 Limitations

| Limitation | Consequence | Mitigation / next step |
|---|---|---|
| No real participants | No evidence of usability, trust or effect | pilot with ethics approval, DPIA and school sign-off (see `docs/ethics/`) |
| Synthetic cohort and labels | Backtest and ML figures measure internal consistency, not clinical validity | prospective evaluation against real outcomes |
| Thresholds not clinically validated | A rule may be too sensitive or too lax for a given school | review with the designated lead; make thresholds configurable per school |
| Small cohort (24 children, 176 ML snapshots, 22 folds) | Wide uncertainty around every metric | larger pilot; report confidence intervals |
| One generator seed (42) | Results may be a property of one synthetic draw | repeat across seeds and report the distribution |
| SQLite | Writes serialise; a large school or a busy cron job would contend | PostgreSQL via the ORM; documented migration path |
| Single school, single tenant | No cross-school isolation or federation | out of scope by design; multi-tenancy would need a separate threat model |
| No uploads, email or push | Some real workflows are excluded | deliberate: each adds a moderation, logging or safeguarding surface |
| Accessibility reviewed against WCAG, not tested with disabled users | Unknown real-world barriers | usability testing with assistive technology |
| No MIS integration | Double entry remains for attendance and marks | future work; CSV import is the smallest safe step |
| `403` distinguishes "exists but forbidden" from `404` | An authenticated user can infer that a child exists | low risk within one school; audited refusals judged more valuable |

Two limitations deserve more than a table row.

**The absence of users is the biggest threat to the project's practical claim.**
The forms are short, the navigation is role-specific and the language avoids
clinical labels, but those are design arguments, not evidence. A child may find
four 1–5 scales intrusive; a mentor may find the queue too noisy; a parent may
not understand why they cannot see a score. A pilot would need to measure
completion rate, time on task, comprehension and trust, and it would need a
protocol for what to do when a child discloses something during the study. That
protocol is exactly what the ethics documents in this repository anticipate.

**The false positives are not free.** Three of fifteen negative children were
flagged at least once. In a real school, each flag is a conversation, and a
pattern of unnecessary conversations can damage the relationship between home and
school. The design reduces the cost by keeping alerts non-punitive, routing them
to a named person and requiring a note to close, but it does not eliminate it.
Threshold tuning against a real cohort, with the false-positive cost made
explicit, is the right response.

## 7.6 Ethical reflection

The project's ethics are mostly in what it refuses to do. It refuses to show a
child a risk label, to give the administrator emotional content, to copy a
disclosure into an alert, to let a message be edited, to auto-resolve a case, or
to connect a classifier to a decision. Those refusals are not neutral: each one
makes some legitimate workflow slightly harder. The argument is that the harder
workflow is the correct one when the data belong to a child.

There is also an ethics of claiming. It would be easy to present the ML metrics
as evidence that the platform can predict which child will become unwell. The
report instead states that the labels are synthetic, the validation is
leave-one-child-out on 22 children, and the model is not deployed. That is less
impressive and more true. The same discipline applies to the backtest: 7/7 recall
is a result about a generator, not a promise to a school.

Finally, the project has no consent from anyone because it has no participants.
The ethics statement in `docs/ethics/` is therefore not a retrospective
justification; it is the protocol a future pilot would have to follow, including
guardian consent, child assent, a DPIA, retention rules and a route for a child to
withdraw. Writing it made the design better: it exposed, for example, that
"consent" in the data model has to mean a current, revocable, versioned record,
not a signature in a filing cabinet.

## 7.7 Implications for practice

For a school considering a system like this, four lessons transfer:

1. **Start with the access matrix, not the dashboard.** The matrix is where the
   school decides what it believes about trust. It is also the cheapest artefact
   to review and the most expensive to retrofit.
2. **Do not give one role everything.** An administrator who can read emotional
   notes undermines the system's promise to children, regardless of intent. The
   head can govern the cohort without reading a diary.
3. **Make absence visible.** "No data" is information. A system that scores an
   unmeasured child as zero will punish the children who most need someone to
   notice they have gone quiet.
4. **End every automated finding with a person.** A queue without owners is a log.
   An alert without a closure rule is a permanent accusation.

## 7.8 Summary

The project's contribution is a working argument that early-warning monitoring
and privacy can be designed together, not a claim that the system is ready for a
school. The evaluation shows that the access model, the scoring method, the alert
lifecycle and the feature set behave as designed on a synthetic cohort. The
limitations are clear enough to state in one paragraph: no real users, synthetic
labels, small sample, unvalidated thresholds, SQLite, one school. The next chapter
sets out what would have to happen to close that gap.
